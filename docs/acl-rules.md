# Authorization baseline (BjyAuthorize + laminas-permissions-acl)

Generated by `tools/acl-table.php` from the merged module configuration plus the `user_role`
table. No timestamp on purpose: this file is meant to `diff` cleanly.

## How to read this

- **Default deny.** `BjyAuthorize\Guard\Route` is enabled, so a route with no guard entry is
  reachable by nobody. Those routes are listed in their own section below.
- **Guards assign, they do not merge.** `AbstractGuard::__construct` does
  `$this->rules[$resource] = [...]`, so when the merged config names the same route in two
  entries the **last one wins outright** and the earlier one is discarded with no warning.
  Merge order is: module config (in `config/modules.config.php` order), then
  `config/autoload/*.global.php`, then `*.local.php`. Every multiply-declared route is flagged.
- **`null` in a roles list means public, not "guest".** `Acl::setRule` turns a null role into the
  `allRoles` pseudo-parent, which `isAllowed()` falls back to for *every* identity — signed in or
  not. So `['user', 'guest', null]` is simply "everyone"; the two named roles are decoration.
- **Effective roles = declared roles + all their descendants.** A child role inherits its
  parent's allows. In `user_role`, `parent_id` points at the *more privileged* ancestor
  (`sch_administrator` → … → `user`), so allowing `user` admits nearly every role.
- The identity is a meta-role (`bjyauthorize-identity`) inheriting the signed-in user's roles
  plus a per-user `user_<id>` role, so "which roles get in" is the right question: holding any
  one effective role is enough.

## Routes served by the Symfony kernel

These paths are matched by `config/symfony/routes.php` before laminas-mvc is ever started, so
`BjyAuthorize\Guard\Route` — a listener on `MvcEvent::EVENT_ROUTE` — never runs for them.
`App\Authorization\RouteGuard` runs on `kernel.request` instead, and asks the ACL about a resource
**each route declares for itself**. That resource is one of the ones above: `route/<name>`, the
same key the laminas guard uses. So the guard entries in this file govern *both* front
controllers, and tightening one tightens both.

Three states, and the third is a bug:

- **checked** — `RouteAccess::guardedBy('route/…')`. The resource column says what it asks about
  and the grant column what that resource allows, copied from the guard table above.
- **open** — `RouteAccess::openToEveryone('<why>')`. No check, stated on purpose, reason shown.
- **undeclared** — nothing at all. `RouteGuard` throws `UndeclaredRouteAccess` when such a route
  is reached, and it is warned about at the top of this file. This is the silent-bypass shape the
  tool exists to catch: a route that lost its guard keeps working and simply admits everyone.

Live only where `SYMFONY_KERNEL=1`: the capsule today, production not yet (docs/strangler.md).
`App\Http\LegacyBridge`, the catch-all that hands everything else to laminas-mvc, is excluded —
it matches every path by design, and laminas-mvc runs its own guard behind it.

#### Why the open ones are open

Each is the string passed to `RouteAccess::openToEveryone()`. Declaring openness is a statement,
not a default, and this is where the statement is reviewed.

- `api-v1/shrines-json` — the laminas guard it shadows is public (a null role admits everyone), and unlike the shrine index this endpoint renders no permission-gated markup, so nothing has already built the ACL. Checking would start a session and run the role/resource queries — some through Books\Model\LibraryTable — on an endpoint the mobile apps poll, for a foregone answer
- `api-v1/shrines-json.locale` — the laminas guard it shadows is public (a null role admits everyone), and unlike the shrine index this endpoint renders no permission-gated markup, so nothing has already built the ACL. - `api-v2/shrines-json.locale` — the laminas guard it shadows is public (a null role admits everyone), and unlike the shrine index this endpoint renders no permission-gated markup, so nothing has already built the ACL. Checking would start a session and run the role/resource queries — some through Books\Model\LibraryTable — on an endpoint the mobile apps poll, for a foregone answer
- `api-v3/association` — shadows no laminas route, so there is no guard entry to consult, and BjyAuthorize reads its identity from a session an agent does not have.
